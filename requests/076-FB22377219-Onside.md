## Descriptive Title

Access to OS-level install verification mechanism for marketplace-distributed apps

## Request Type

Interoperability Request

## Feature Requested

iOS System-Level Install Verification and Attestation Capability (cryptographic install authenticity mechanism)

## Reason for Request

iOS includes a system-level capability that generates cryptographically signed attestation for app installations. This attestation serves as verifiable proof that an app was legitimately installed through a trusted distribution channel and is relied upon by developers and measurement partners to detect fraud and validate installs.

This request does not seek access to raw security signals or internal fraud detection systems. It seeks access to the same OS-level install attestation capability that iOS already provides to the App Store.

Apps distributed via the App Store benefit from OS-level install verification that is independently verifiable and trusted across the ecosystem, whereas apps distributed via alternative marketplaces cannot provide equivalent proof of authenticity.

The relevant functionality is therefore the OS-level generation of cryptographically verifiable install attestation and its provision to apps and developers, which constitutes a system-level capability controlled by iOS and currently available to the App Store and its users.

## Product Description

Onside — an alternative app marketplace for iOS that enables developers to distribute their apps outside the App Store within the EU.

## How the Feature Will Be Used

Onside will use the OS-level install verification to provide developers with install authenticity equivalent to App Store receipts:

* **Install fraud prevention:** Developers and MMPs will be able to validate cryptographically signed receipts to distinguish legitimate Onside installs from fraudulent installs, bot-generated events, and device farm attacks — equivalent to how App Store receipts are used today.
* **Marketing attribution trust:** Developers will be able to provide verification receipts to attribution partners, enabling accurate marketing measurement for apps distributed via Onside — equivalent to the trust level that App Store receipts provide.

## Where Offered

European Union

## Evaluation of Alternatives

There are no viable alternatives. The install verification mechanism relies on two things that only Apple controls:

* **OS-level receipt generation:** App Store receipts are generated by iOS at the operating system level using Apple’s private cryptographic keys. The install verification mechanism relies on OS-level cryptographic attestation that can only be generated and signed within iOS. Third parties cannot replicate this functionality outside the operating system, as they do not have access to system-level attestation mechanisms.
* **Independent trust:** Even if alternative marketplaces attempt to generate their own verification tokens, such tokens would not carry independent trust, as they are not issued by the operating system and cannot be cryptographically verified against a system-controlled authority.

Only Apple can extend the OS-level install verification feature to apps distributed through alternative marketplaces.

## Confidentiality

Fully available to other developers

## Additional Information

Privacy Safeguards:

* Install attestation data will contain only minimal installation metadata (app ID, install time, version). No individual user identifiers or personal data will be included.
* All access would be subject to iOS entitlements, audit logging, and EU GDPR requirements.

Technical Details:

* iOS already generates cryptographically signed install receipts for all App Store installations. The infrastructure exists and is operational.
* Apple can extend access to the same receipt generation for apps distributed through authorized alternative marketplaces, delivered via API.

Success Criteria:

* Onside-distributed apps receive cryptographically signed install verification receipts with security properties equivalent to App Store receipts.
* Developers and MMPs can validate receipts using Apple-provided public keys.
* Receipt generation occurs automatically at OS level without requiring per-app SDK integration.

##### May 26, 2026 — Developer to Apple

Dear Apple DMA Interoperability Team,

We request an internal review of Apple’s decision to close interoperability request FB22377219, “Access to OS-level install verification mechanism for marketplace-distributed apps.” Specifically, we request the application of the Dispute resolution mechanism pursuant to Section 3.2, paragraph 20(a), of the Commission decision in case DMA 100204 SP - Apple - Article 6(7) - Process.

Apple’s response states that effective interoperability already exists because developers and their chosen partners can use App Attest. We respectfully disagree with this assessment.

For clarity, the functionality we requested is analogous to Apple’s App Store receipt validation mechanism described in Apple’s documentation, including “Validating receipts on the device”: <https://developer.apple.com/documentation/AppStoreReceipts/validating-receipts-on-the-device>.

We are not requesting a developer-specific app-integrity challenge-response framework. We are requesting an OS-level, Apple-generated, cryptographically verifiable receipt or attestation object that evidences legitimate installation/download provenance for apps distributed through an authorized alternative marketplace.

App Attest is not functionally equivalent to the requested App Store receipt-style functionality.

App Store receipt validation is based on an Apple-generated signed object representing app, download, and transaction-related state. App Attest, by contrast, is a developer-specific app integrity and request-attestation framework. It verifies that requests originate from a legitimate instance of an app running on an Apple device, but it does not attest the installation channel, marketplace provenance, or download event.

The difference is material:

* App Store receipt validation provides an Apple-signed object representing app / transaction / download-related state.
* App Attest provides a developer-specific app integrity and request-attestation flow.
* App Attest requires each developer to implement and operate backend services, challenge-response handling, key lifecycle management, attestation validation, and partner integrations.
* App Attest does not allow an MMP or other relying party to independently verify install provenance without bespoke developer-side infrastructure and data sharing.
* App Attest is distribution-channel agnostic and does not prove that an app was installed through Onside or any other authorized alternative marketplace.

For these reasons, App Attest may be useful as a complementary anti-fraud tool, but it does not provide effective interoperability with the OS-level install verification capability requested in FB22377219.

The requested functionality is a system-level install provenance mechanism: an Apple-generated, cryptographically verifiable receipt or attestation confirming that an app was legitimately installed through an authorized alternative marketplace, with security properties comparable to App Store receipt validation.

Apple’s proposed alternative shifts the implementation burden from Apple’s OS-level distribution infrastructure to each individual developer and their backend systems. That is not equivalent to providing standardized OS-level interoperability for alternative marketplaces, developers, and measurement partners.

We therefore ask Apple to initiate the internal review mechanism for this decision and to provide the next procedural steps, including any required format or submission requirements for the appeal.

##### September 7, 2026 — Developer to Apple

Dear Apple DMA Interoperability Team,

Thank you for your update on FB22377219 and for moving part of the request to the next phase. To avoid any misunderstanding about the requested functionality, we would like to clarify the current technical comparator and the remaining interoperability gap.

We agree that the legacy binary App Store receipt APIs have been superseded by AppTransaction. The current functionality to which our request should be compared is specifically VerificationResult<AppTransaction>.jwsRepresentation: an App Store-signed JWS that is available to the installed app and can be sent to a backend for independent cryptographic verification.

There is currently no equivalent for an app installed through an alternative marketplace:

* The MarketplaceKit installVerificationToken is generated and signed by the marketplace before installation and supplied to iOS as an input to the installation request.
* The installVerificationToken is not made available to the installed app and does not constitute an iOS-signed confirmation that installation was completed.
* A record generated and signed by the marketplace proves only that the marketplace created or authorised an installation request. It does not prove that iOS completed that installation.
* AppDistributor.current allows the installed app to determine its distribution source locally, but it does not provide an Apple/iOS-signed JWS that can be transmitted to and independently verified by the publisher, its MMP, or the marketplace backend.

The interoperability functionality requested in FB22377219 is therefore an Apple/iOS-signed, server-verifiable installation object that:

1. is available to the installed app;
2. identifies the alternative marketplace through which the app was installed;
3. confirms that iOS completed the installation; and
4. can be transmitted to a publisher, MMP, or marketplace backend for independent verification.

We note that your update moves the request forward with respect to “the discrepancy in the install verification receipt identifier that alternative app marketplaces receive.” Could you please confirm whether the next-phase assessment covers the signed, app-accessible and backend-verifiable object described above, rather than only an identifier or record supplied to the marketplace?

If the contemplated solution concerns only an identifier, we would appreciate clarification on how the installed app would obtain that identifier and how a backend would independently verify both its authenticity and the completion of the installation.

We would be happy to provide any additional technical detail or proposed data model that would assist the next-phase assessment.

##### October 23, 2026 — Apple to Developer

Following on our communication of August 27, 2026, we have now completed our assessment in phase II and are moving your request to the next phase of our interoperability process. You will find further information on the planned interoperability solution and the next steps below.

We will introduce new MarketplaceKit APIs that will enable alternative app marketplaces and the apps they distribute to access a new installation identifier. This installation identifier will be a stable identifier that persists for the duration of the install and can be used to validate the installation of an app. The changes consist of:

* MarketplaceKit API addition to AppLibrary.App.Metadata that allows the app marketplace to access the installation identifier for a given app which it has installed.
* MarketplaceKit API addition to AppDistributor that installed apps can use to access the installation identifier for themselves.

To adopt this solution, you will need to be able to use the installation identifier from the app marketplace and from the installed app to verify that the identifiers match, ensuring the app was installed from the app marketplace in question. Clearly, any verification and signing of the installation identifier would need to be handled directly between you as the app distributor and the installed apps. This is equivalent to how the App Store handles verification and signing of installation identifiers using backend server-side processing that is not within the scope of Article 6(7) DMA.

This is a mild engineering effort. We plan to complete the development of this solution ahead of October 2027 and would ship it shortly thereafter in a developer-facing beta release prior to full release. We will update you once we have shipped it in a beta release.

We believe this addresses your request. Please let us know within 5 working days by responding to this email if you have any feedback on the proposed plan. If we do not hear from you in that time frame, we will begin development work in accordance with the plan described above.

After providing feedback and Apple’s response to the feedback, if you still consider that the Project Plan would not provide a solution equally effective compared to the feature (including any of its functionalities) used by Apple, you will have the opportunity to initiate a dispute resolution mechanism.
