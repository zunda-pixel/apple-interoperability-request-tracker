## Descriptive Title

Request for deterministic background execution for connected device scenarios such as enabling cross-device copy/paste or recent photo syncing

## Request Type

Interoperability Request

## Feature Requested

Background execution for features like Universal Clipboard

## Reason for Request

To meet our user needs, Microsoft needs the ability to keep the user’s devices up to date when content changes on one or the other. For example, the ability to push clipboard or file data from the Windows PC to the iOS device or sync new photos and videos from the iOS device to the Windows PC.

To achieve this in a seamless way, Microsoft needs the ability for the PC to deterministically gain background execution time on the phone to perform actions that may-or-may-not be long-running.

## Product Description

Windows, a general-purpose personal computing platform used globally for productivity, communication, and multi-tasking across consumer and enterprise scenarios.

## How the Feature Will Be Used

Windows would use deterministic background execution and background refresh on iOS to enable seamless, user-initiated cross-device scenarios that keep an iPhone and a Windows PC in sync without requiring users to foreground an app or repeatedly take manual actions. These scenarios are already supported by Apple within its own ecosystem — for example, between iPhone and macOS — where system-level background execution enables continuous features such as Universal Clipboard and access to recent photos and files across devices. Windows is seeking the ability to leverage similar background refresh capabilities on iOS to enable equivalent cross-device productivity scenarios for users who choose a Windows PC alongside their iPhone.

For example, this capability would enable:

* **Cross-device copy and paste:** When a user copies content on their iPhone, background execution would allow the connected Windows PC to be notified and receive that content in near real time, so it is immediately available to paste when the user switches to their PC. Similarly, content copied on the PC could be made available on the phone without requiring the user to foreground an app or explicitly initiate each transfer.
* **Access to recent phone files and photos on PC:** Background execution would allow the Windows PC to stay up to date with newly captured photos, videos, or recently accessed files on the iPhone.

In all cases, background execution would be used only to support user-initiated continuity scenarios and lightweight synchronization. The intent is to enable reliable, timely updates that make cross-device interactions feel immediate and natural — consistent with the experience Apple already provides across iPhone and Mac — while respecting system constraints, user control, and privacy expectations.

## Where Offered

European Union

## Evaluation of Alternatives

Yes.

* Background execution frameworks offered by iOS are focused on continuing foreground work in the background or for operations that are infrequent or are not time-sensitive.
* There are no triggers available on iOS that will grant an app execution time when user content, such as photos or files, changes. This forces a need for a polling approach to monitor changes to content.
* There are no acceptable frameworks for an external device such as a PC to reliably “wake” our app’s process with any reasonable frequency on iOS to transmit data to or from the device. BluetoothLE background modes are the closest available approximation but the execution time granted is limited and documentation is unclear about how frequently the channel can be utilized without throttling or degradation of experience. For example, with Universal Clipboard, changes may be frequent.

##### July 15, 2026 — Apple to Developer

Please find our responses below:

1) Whether an app can be woken promptly when Photos or videos change on device.

The Windows app will not be woken for every library change. Syncing is designed to trigger based on the user’s own interaction with their Windows device — not arbitrary content changes on the iPhone — so your app can collaborate with the system to sync photos/videos when the user intends it, while preserving battery life and cellular data usage. Polling or waking on every library change is neither scalable nor necessary for an equivalent experience.

Three tools support this:

* The new silent push notification proposed here, scoped to cases showing user intent to interact with photos on a connected device.
* Live change observation via PhotoKit while your app is running — for example, when launched in response to the silent push above.
* The new Photos syncing API in iOS 26.1 (PHBackgroundResourceUploadExtension), which accounts for full system state before syncing.

This mirrors how our own first-party syncing works.

2) Whether any API exists for observing real-time Photos changes without polling.

PhotoKit does support live change observation, but only for an active process (<https://developer.apple.com/documentation/photokit/observing-changes-in-the-photo-library>). It also supports querying historical changes, avoiding the need to poll the full library (<https://developer.apple.com/documentation/photos/phphotolibrary/fetchpersistentchanges(since:)>).

3) How silent push differs from existing background push.

Unlike Content Available pushes, this new push type is only sent to the iOS device when photos/videos actually need uploading — not on every library change. This targeted delivery is core to balancing UX with system integrity.

4) Execution guarantees silent push provides.

Apps using AccessorySetupKit get sufficient background execution time to upload via URLSession or PHBackgroundResourceUploadExtension, under conditions mirroring first-party syncing restrictions.
